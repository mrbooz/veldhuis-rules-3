# Postmortem: Nordkant weekly export, w/c the 13th

## What happened, and what changes

What happened: the Sunday reconciliation refused the Nordkant w/c-13th file at 23:40 — every hour priced correctly, but for three drivers whose shifts cross midnight the applied-rules record covered only the half of each night before the boundary, so the file could not account for the other half and the audit did its job. Nothing transmitted; the 06:00 send was held at 23:52 and stays held until the record is complete and the file re-reconciles. Why: the applied-rules change recorded per evaluate() call, and the Nordkant export divides a crossing shift and calls evaluate once per half — but the serialiser that writes the outbound record reads span.ts's second call site, which has never been in any reviewed diff, and it kept only the first half's list. The review that accepted the recording change — mine — checked the criteria against the file it changed and did not walk the call sites; the criteria said 'no number changes' and no number changed. The audit caught what the review did not, which is the system working, one layer later and one day slower than it should. What changes: (1) the applied-rules record becomes per-shift, an ordered list per half merged by the caller that divided it — the fix is on the branch, held with the file. (2) The serialiser in span.ts's export path enters review scope: CODEOWNERS gets a line so no outbound-file change ships unreviewed again. (3) The reconciliation rule that caught this is promoted from the haulier export to every customer export before the next rota cycle — it is the only check we have that reads the file the customer reads. No names: the change did what its criteria said; the gap was in what the criteria did not say, and the person who wrote those criteria is writing this.
